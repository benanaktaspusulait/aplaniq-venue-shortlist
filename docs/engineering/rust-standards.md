# Rust engineering standards

These rules apply to all implementation, tests, reviews and packaging. The [assessment requirements and approved working policies](../requirements.md) govern product behaviour. Read this document before editing. Use the [quality gate](quality-gates.md), [task backlog](../tasks/README.md) and [assessment log](../assessment-log.md) to plan and record work.

## Governance and toolchain

- For every implementation task, review requirements, confirm scope, record a focused plan, add relevant tests, inspect the actual diff, run the gates and commit the verified change. Record trials, actual agents and limitations. The assessment requires Claude Code for business implementation and business corrections. Codex may audit, plan and enforce engineering standards. Disclose historical deviations and use only genuine planning artifacts.
- Classify requirements as **mandatory**, **conditional**, **not applicable** with a reason, or **blocked** with the concrete limitation. A conditional check is mandatory once its conditions hold. Record when it cannot run. Never report a blocked or inapplicable check as passing or silently weaken a standard.
- Use Rust Edition 2024, the exact stable version in [rust-toolchain.toml](../../rust-toolchain.toml) and the verified MSRV in [Cargo.toml](../../Cargo.toml). Keep local, CI and optional Docker builders aligned. Prove MSRV support with the locked graph on that compiler. Stable language features and standard-library APIs must also support the MSRV. For example, `let` chains require Rust 1.88 and the current floor is 1.85.0. Global tooling installation or upgrades require authorisation. [Rust release notes](https://doc.rust-lang.org/stable/releases.html) · [Rust 1.88 release](https://blog.rust-lang.org/2025/06/26/Rust-1.88.0/#let-chains)
- Prefer exhaustive matching, `let else`, `?`, simple combinators and iterators, type inference, derives, standard collections and useful const functions where they clarify behaviour. Use stable features only. The pinned compiler and official documentation govern APIs and syntax.

## Architecture, domain and API

- Maintain one Cargo package with a reusable `venue_shortlist` library and thin `venue-shortlist` CLI. Modules are cohesive units inside a crate. External crates are Cargo dependencies. Follow the [module boundaries](../architecture.md#module-boundaries). CLI calls application orchestration, which uses the domain. Ingestion and recommendation depend on domain types. Keep the domain free of raw JSON, CLI, terminal formatting, filesystem, infrastructure and network dependencies. Keep dependency direction acyclic.
- Use structs, private invariant-bearing fields, validated constructors and newtypes for domain values. Keep owned behaviour in `impl` blocks. Use closed enums and composition. Apply separation of responsibilities and interface segregation pragmatically. Use traits, associated types and static polymorphism for concrete contracts. Use pure functions for deterministic calculations and transforms. Avoid speculative traits, generic persistence and service layers, dependency injection frameworks, artificial inheritance and dynamic dispatch.
- Default to private visibility, use `pub(crate)` or narrower visibility inside the crate, and expose a deliberate public API. Public fields are suitable for data carriers whose invariants do not need protection. Document useful public items and non-obvious contracts. Use UpperCamelCase for types and traits, snake_case for functions, variables and modules, and SCREAMING_SNAKE_CASE for constants and statics. Prefer explicit imports and a focused `lib.rs`.
- Use `as_*` for inexpensive borrowed conversions, `to_*` for conversion to another representation and `into_*` for consuming conversions. Derive traits only when their contracts hold. Keep `Eq` and `Ord` consistent, use `From` for infallible conversion and `TryFrom` for fallible conversion. Use `Default` for a meaningful default and `#[must_use]` when discarding a result is likely an error. Add builders, sealed traits or `#[non_exhaustive]` only for an actual compatibility or construction need.
- Preserve distinct missing, unknown, invalid, unsupported, contradictory, positive and negative evidence. Keep seated capacity separate from standing. Use `Option` for real absence and `Result` for fallible operations. Never default unknown prices or capacity to zero or imply confirmed access or availability from uncertain evidence. Use checked integer minor units or justified exact decimals for money, never binary floats. Preserve pricing basis, currency, minimum spend, VAT and catering. Check overflow and narrowing conversions. Type-state and additional wrappers require an actual misuse risk.

## Ownership, errors and input

- Borrow first with `&str`, slices and `&Path`. Own values when a caller needs to retain them. Use conversions with `Into` or `AsRef` when they improve the API and justify non-trivial clones. Prefer immutable bindings and simple lifetimes. Avoid allocations, indirection, shared ownership, concurrency, async and release-profile tuning without evidence. The workload is roughly 30 local JSON rows. Keep performance and overflow behaviour predictable in debug and release.
- Cargo forbids first-party unsafe code in every target. Never add unsafe blocks, functions or implementations, FFI, raw pointer manipulation or manual memory management. The policy does not establish that dependency code is unsafe-free.
- Production code must handle errors without `unwrap()`, `expect()`, `panic!()`, `todo!()`, `unimplemented!()` or `dbg!()`. An invariant exception requires narrow scope, documentation and approval where applicable. Unsafe code has no exception. Check indexing, UTF-8 boundaries, date construction, arithmetic and conversions on external input. Preserve error sources, path, record identity, field and cause where relevant. Use typed errors and standard-library error chains before adding crates. Keep normal outcomes such as an empty valid shortlist separate from unreadable or invalid documents. Print results to stdout and actionable errors to stderr. Keep secrets, unnecessary raw input, network clients and runtime AI out of the application.
- Preserve `venues.json` and account for every source row. Separate parsing, normalisation, deduplication, eligibility, ranking and output. Preserve relevant negative and contradictory claims and their provenance. Keep eligibility separate from scoring and show provisional, confirmed and rejected outcomes distinctly. Implement the 80 and 120 scenarios under the approved policies. Use explicit dates and a stable total ordering and tie-breaker. Avoid dependence on hash iteration, wall clock, locale, network or machine-specific paths.

## Dependencies and packaging

Verify purpose, actual usage, selected version, features, compiler compatibility, upstream maintenance, licence and advisory status before adding or updating crates. Prefer the standard library where sufficient. Declare test-only dependencies separately and add build dependencies only when required. Keep `Cargo.lock` committed and `publish = false`. Inspect the locked graph, duplicates and features. Evaluate duplicates with their impact. Avoid speculative proc macros or frameworks, untrusted registries and unjustified Git or path dependencies.

| Direct crate | Use and reviewed configuration |
| --- | --- |
| `chrono` 0.4.45 | Provides validated `NaiveDate` and `Weekday` used by the domain and availability parser. The standard library has no equivalent. Defaults are disabled. Upstream declares Rust 1.62 and MIT OR Apache-2.0. [Registry](https://crates.io/crates/chrono/0.4.45) |
| `serde_core` 1.0.229 | Already in the lockfile. Exposes the map visitor interface needed to find repeated keys before collapse. Defaults are disabled. Upstream declares Rust 1.56 and MIT OR Apache-2.0. [Registry](https://crates.io/crates/serde_core/1.0.229) |
| `serde_json` 1.0.154 | Parses heterogeneous JSON and retains numeric text for exact minor-unit conversion. Uses `std`, `arbitrary_precision` and `raw_value` to also inspect source object keys. No standard-library JSON parser. Upstream declares Rust 1.71 and MIT OR Apache-2.0. [Registry](https://crates.io/crates/serde_json/1.0.154) |

The locked releases are checked against the pinned compiler and the project MSRV. Supply-chain checks are defined in the [gates](quality-gates.md). Review the consequences of changing precision, parsing or clock features.

[Optional Docker packaging](../tasks/TASK-007B-docker-packaging.md) is subordinate to the native deliverable. Match the pinned Rust builder, verify linkage against the runtime base, use a locked multistage release build and run as non-root with read-only external input. Test argument forwarding, help, invalid-input exit status, network-free execution and native parity. Exclude sources, secrets, agent history and assessment material from the runtime image. No publishing or deployment.

## Tests, lint policy and reviews

- Add focused Rust unit tests near the code and integration tests under `tests/`. Map acceptance criteria to meaningful assertions. Cover relevant failure and boundary cases, zero or negative input, exact money and capacity boundaries, overflow, Unicode, missing and duplicate IDs, unsupported or contradictory fields, date validity, deterministic ranking, reasons and empty outcomes. Preserve the original export integration test and cover v019 end to end without special-case production logic.
- Include regressions for real defects where practical. Use small deterministic fixtures, clear names and focused arrange-act-assert tests. Avoid brittle snapshots and network or order dependencies. Never remove, ignore or rewrite a test because its assertion failed. Add CLI tests when implemented. Use property testing and specialised tools only for meaningful gaps. Coverage percentages, if measured, supplement business coverage.
- [Cargo lint policy](../../Cargo.toml) forbids unsafe, denies unsafe operations in unsafe functions and unused must-use results, and warns on missing docs. Clippy denies `all` and specified production panic or debug macros and warns on `pedantic`. The gate promotes warnings to errors. [Test configuration](../../clippy.toml) allows fixture unwraps, expects and test panics. Keep the debug macro banned. Use no blanket suppressions. Prefer a precise `#[expect]` for an evidenced exception where supported, and document its lint, location, reason, impact and why refactoring is worse. Rustdoc includes applicable Errors, Panics, Examples or Safety sections only.
- Keep [R1–R4](../tasks/README.md#engineering-review-checkpoints). Review actual source, tests, architecture, invariants, errors, security, deterministic behaviour, dependency trust, performance, docs and packaging where applicable. Record each finding's ID, severity, location, evidence, impact, recommended correction, regression and resolution. Use a separate context or reviewer for independent review and label self-review accurately. Unresolved critical correctness or security findings block subsequent implementation.

Commit independently reviewable changes and relevant tests. Inspect status, staged and unstaged diffs and actual gate output. Stage exact paths, preserve pre-existing staged changes and exclude secrets. Preserve genuine history including failed attempts. Push only with explicit authorisation.
